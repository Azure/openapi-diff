### 1025 - RequiredStatusChange

**Description**: Checks whether an existing property's `required` status is changed from the previous specification. 

**Cause**: Under this rule's semantics, this is considered a breaking change in the same api-version but not in a new
api-version. This does not by itself define Azure REST API breaking-change policy.

**Important — Azure policy**: Requiredness changes affecting the wire contract can still require breaking-change review
in a new API version. Azure policy treats changing existing input/output fields from required to optional as
breaking-change review cases. In particular, do not assume required-to-optional changes to response/resource fields
are automatically safe just because the api-version changed.

Azure specs policy and validation runner mapping can treat `RequiredStatusChange` as breaking in PR validation.
The example below illustrates rule semantics, not the full Azure review policy. A finding in a new API version is not
by itself evidence of a tooling/documentation mismatch; follow the Azure breaking-change review process rather than
starting with suppression unless there is grounded evidence that the finding is incorrect.

**Example**: `required` status for parameter `b` is changed from `false` to `true` without revising api-version.
